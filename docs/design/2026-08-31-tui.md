# A TUI for tdy — design proposal (for discussion)

Status: **proposal, not started.** Steps 1 and 2 of the comfort work — the
`PileReport` layer with `--json`, and the MCP server — are in. This document
is the third: what a terminal UI should be, argued from what tdy is, so the
discussion can be about the decisions rather than the pixels.

## 1. What the TUI is for

tdy's human workflow is a *review loop*: declare → fit → read the report →
make a judgement (an alias, an exclusion, an acceptance) → re-fit. Today
every arrow in that loop is "read terminal output, edit a file, re-run".
The TUI's job is to collapse the loop's latency — not to add capability.
Everything it does must be something the CLI can already do; if a feature
only works in the TUI, it is in the wrong layer.

Three moments carry almost all of the value:

1. **Seeing the pile.** Which files fit, which wait on a human, which are
   refused and why — as a living table rather than scrollback.
2. **Closing a gap.** "`amount_chf` binds nothing" is answered by *looking
   at the file*; the TUI can put the gap report and the file's actual head
   rows side by side, and turn the remedy (add a `matches` alias, exclude
   the file, declare `if_missing`) into a keystroke that edits the target.
3. **The acceptance.** The review gate's meaning is that a human *reads*
   before saying yes. This screen is the heart of the TUI and the one place
   where design must add friction rather than remove it.

## 2. Invariants (the part that is not up for discussion internally)

These come from the project's design and the TUI must not erode them:

- **A view over the artifacts, never a parallel store.** All state lives
  where it already lives: the target `.tdy.sql`, the sidecars, the lock.
  Every TUI action is expressible as "edited this file, ran this function",
  and a session leaves behind exactly what a CLI session would — so the git
  diff after a TUI session reads like any other. No hidden database, no
  session file, no TUI-only annotations.
- **The TUI renders `PileReport`.** One orchestration (`report::fit_pile`),
  three renderers (CLI text, JSON, TUI). The TUI never re-implements fit
  logic, never computes its own status.
- **Acceptance shows the evidence.** The accept screen must display the
  actual consequence of the judgement — the rows before and after the
  `decimal_shift`, the constant value being asserted into every row, the
  frame the model chose with the rows it captures — and the review reason
  verbatim. No bulk-accept. No accept from the pile view. You accept a
  member from *inside* its evidence screen, one at a time. (The CLI lets
  you `--accept` blind; the TUI, whose whole point is showing, should not.)
- **Edits to the target are shown as a diff before they are written.** The
  target is reviewed-in-git material; the TUI writes it the way a careful
  human would — visibly.

## 3. Screens

A single-window app, four screens, `Tab`-cycled, all reachable from a pile
overview. Layout sketches assume ~100 columns.

### 3.1 Pile view (home)

```
 sales.tdy.sql — 12 files, 3 columns                      9 fit · 1 review · 2 refused
┌──────────────────────────────────────────────────────────────────────────────────────┐
│   2025-01.csv   fits      month←Datum  region←Region  amount_chf←Betrag              │
│   2025-02.csv   fits      …                                                          │
│ ▸ 2025-07.csv   REVIEW    decimal_shift = -2 changes every value          [enter]    │
│   2025-08.csv   REFUSED   `amount_chf`: two columns named Betrag          [enter]    │
│   2025-11.csv   REFUSED   `region`: no column of this file binds          [enter]    │
│   …                                                                                  │
└──────────────────────────────────────────────────────────────────────────────────────┘
 [enter] inspect   [f] re-fit   [t] edit target   [q] query   [?] help
```

- Populated by one `fit_pile(dry_run: true)` on startup; `f` re-runs it for
  real (writing sidecars/lock) with a progress line per member.
- Statuses use the `MemberStatus` enum verbatim. No TUI-invented states.

### 3.2 Member inspection (gaps and evidence)

Split view: left the problems (from `Problem`, structured), right the file
itself — the post-transform head rows tdy actually sees, header highlighted.

```
┌ 2025-11.csv — REFUSED ────────────────┬─ what tdy sees ──────────────────────────────┐
│ `region` (TEXT): no column binds      │  Datum       Betrag                          │
│   looked for: region, Kanton, Gebiet  │  30.11.2025  2'100.00                        │
│   remedies:                           │  30.11.2025  2'110.00                        │
│   [m] add a matches= alias …          │  30.11.2025  2'120.00                       │
│   [n] declare if_missing = 'null'     │  …                                           │
│   [x] exclude this file               │                                              │
└───────────────────────────────────────┴──────────────────────────────────────────────┘
```

- Each remedy key opens a prompt, then shows the **target diff** and asks to
  write it. Writing triggers a re-fit of the pile (cheap now: fresh sidecars
  are reused).
- For an `ambiguous`/`ambiguous_frame` problem, the choices are listed and
  choosing writes the sidecar (pointer/sheet/`Betrag_2`) as `method =
  "manual"` — the same artifact a human would write by hand.

### 3.3 The accept screen

Reached only from a REVIEW member's inspection. Shows, in this order:

1. The review reason, verbatim.
2. The evidence: for a `decimal_shift`, a two-column table of raw value →
   parsed value for the head rows *and the largest and smallest values in
   the file* (the rows a wrong shift would distort most); for a `constant`,
   the value and the row count it will be asserted into; for a model frame,
   the frame description and the first rows it captures.
3. The consequence sentence: "accepting records this judgement against
   these bytes; editing the file or the spec retracts it."

`a` accepts (runs `fit_pile` with that member in `accept`), anything else
backs out. Deliberately no "accept all".

### 3.4 Query scratchpad

A one-line SQL input over the current target's `dataset()` (or any
`messy()`), result table below, `LIMIT` injected when absent, row cap as in
MCP. History with `↑`. This is a convenience, not a SQL IDE; results are
read-only and never exported from here (that is `tdy query -o` territory).

## 4. Architecture

- **Separate crate** (`tdy-tui`, workspace member), so ratatui + crossterm
  stay out of the core dependency tree and out of the crates.io package.
  The binary is `tdy-tui`; `tdy ui` can exec it if found on PATH (the way
  cargo does subcommands) — to be discussed.
- **ratatui + crossterm**, immediate-mode, one event loop.
- **Work happens off the UI thread.** `fit_pile` on a big pile does real
  I/O (whole-file verification); it runs on a worker (tokio task — the lib
  is already async because of `plan`) and sends progress + the finished
  `PileReport` over a channel. The UI never blocks; a running fit shows a
  per-member spinner using the same order the report will have.
- **File watching, maybe.** Re-fit on target/sidecar change (notify crate)
  would make the "edit in `$EDITOR`, alt-tab back" loop seamless. v2.
- **No config.** Keybindings fixed, colors from the terminal theme.

## 5. What the TUI deliberately does not do

- **No spec editor.** Sidecars are TOML with a schema and good validation
  errors; `$EDITOR` (spawned suspended, like `git commit`) beats a bespoke
  form. The TUI's `e` on a member opens the sidecar in `$EDITOR`, then
  validates and re-proves on return.
- **No draft wizard in v1.** `tdy draft` output is already a commented file
  meant for an editor. A later "merge these two columns" interaction on top
  of the draft is the most tempting v2 feature — flagged for discussion.
- **No mouse-first design.** Keys, with a help line always visible.

## 6. Open questions (the discussion)

1. **Does the accept screen need more teeth?** Options considered: require
   scrolling through the evidence before `a` activates; require typing the
   member name (like GitHub's "type the repo name to delete"). My lean: the
   evidence-first layout is enough; ceremony that gets muscle-memoried is
   worse than none. But this is exactly the judgement the discussion is for.
2. **Multi-target.** One TUI session = one target file, or a workspace view
   over every `.tdy.sql` under the cwd? Lean: one target; a picker at
   startup when several exist.
3. **The `tdy ui` exec shim** vs telling people to install and run
   `tdy-tui`. Lean: shim, it costs ten lines.
4. **Where does `draft` fit in?** A "no target yet" start screen could run
   draft on a chosen pile and drop into the editor. Cheap and useful, or
   scope creep? Lean: v1.5.
5. **Live progress for the LLM tier**: when a frame proposal is running,
   the TUI should say a model is being consulted and what was sent (the
   CLI prints this today). Needs `plan` to emit progress events instead of
   `eprintln!` — a small `Progress` callback in `Config` or a channel
   parameter. Worth doing for the MCP tier too (as MCP progress
   notifications). Decide once, here.

## 7. Effort

Roughly: pile view + inspection read-only in a day or two; remedies-as-
target-edits and the accept screen another two; scratchpad and polish one
more. The `Progress` plumbing (question 5) is a small core change best done
first if agreed.
